# 金融风控 RL 实验规划讨论材料

## 1. 当前结论

我们已经完成了 RL 训练诊断工具的最小工程闭环：能够读取训练日志，解析实际训练参数，解析 rollout JSONL，恢复同一 prompt 的 rollout group，统计 reward 是否提供组内区分信号，并通过 Jupyter 和浏览器看板展示训练过程。

目前还没有完成可以支持算法结论的实验闭环。之前的 5 step GRPO 实验只能证明训练链路能够运行，不能证明模型效果提升，也不能证明 GRPO 不适合当前任务。该实验中低信息 group 占比较高、全错 group 较多、输出截断较明显，而且训练步数不足以触发大部分稳定性规则，因此下一步应先完善实验配置记录，再进行正式的金融风控基线实验。

## 2. 已完成的工具能力

- 训练日志与动态参数解析：算法、模型、数据集、rollout 数量、batch size、学习率、训练 step 和 step 指标。
- rollout JSONL 解析：prompt、response、reward、pred、acc、group_id、rollout_id 等字段。
- group 级诊断：全对、全错、接近全对、接近全错、全同 reward 和低信息 group。
- 训练指标监控：平均 reward、reward 范围、reward 波动、KL、entropy、gradient norm、截断率和有效回答比例。
- 训练稳定性规则：区分“已触发”“未触发”和“样本不足、暂不能评估”。
- 实验对比：支持比较不同实验的参数、最新指标和 step 趋势。
- 原始证据查看：能够按 step 查看 prompt、模型输出、reward、pred 和 acc。
- NGRPO 运行时 patch、Jupyter 监控和浏览器前端看板。

## 3. 前端下一步改进

前端不应只展示一个孤立的 reward 数字，而应让使用者知道“这个数字是什么、来自哪一步、是否能用于比较”。计划增加以下配置和事实展示：

- 明确显示算法；如果命令未记录，则从 VERL resolved config 恢复。
- 将 reward 显示为“最新 Step 平均奖励”，同时显示该 step 的最小值、最大值和标准差。
- 显示 Reward 定义、理论最小值和最大值，区分训练 reward 与独立评测准确率。
- 显示任务领域、任务类型、数据特征维度、是否包含 CoT、随机种子、训练预算和 NPU 数量。
- 显示镜像版本、patch 版本和代码版本。
- 增加“具备算法对比条件/暂不具备严格对比条件”的提示，并列出缺失字段。
- 新实验生成 `run_manifest.json`，作为实验元数据的权威来源；旧实验缺失的信息显示“未记录”，不进行猜测。

前端的“对比资格”只表示实验条件记录完整，不表示实验已经证明某个算法更好。

## 4. 金融风控实验目标

实验方向从数学题切换为“根据注册公司的多维财务和经营数据进行风险分析”。建议先把任务定义成一个可验证的单一任务，而不是一开始同时训练多个风控任务。

推荐的首个任务是：

> 给定企业的结构化财务、经营和登记信息，输出风险判断、风险等级或风险分数，并给出基于输入字段的简洁分析依据。

首轮实验需要先明确：

- 是二分类、三分类、风险排序，还是连续风险评分。
- 标签来自人工审核、历史逾期/违约、授信结果，还是其他业务结果。
- 训练目标是预测历史标签，还是生成可供审核人员阅读的风险分析报告。
- 是否需要输出置信度、风险因素、建议动作和证据字段。
- 评测重点是召回高风险企业、控制误报，还是综合排序质量。

如果这些问题没有确定，无法合理设计 reward，也无法判断 RL 是否比 SFT 更合适。

## 5. 数据集最低要求

“30 多维特征”本身不是数据集适合 RL 的充分条件。数据还需要有可靠标签、清晰的输入输出协议和可验证的评分方式。

建议每条样本至少包含：

```text
sample_id
company_id 或脱敏企业标识
feature_schema
features
label 或 risk_level
label_time
observation_time
data_split
```

如果使用 CoT 训练数据，还需要明确：

```text
prompt
response 或 reasoning_trace
final_answer
ground_truth
verifier/evaluation fields
```

数据集应满足：

- 训练、验证、测试按企业主体或时间切分，不能让同一企业的相近记录跨集合泄漏。
- 明确缺失值、异常值、极端值和字段单位。
- 记录每个字段的含义、取值范围和时间口径。
- 不把企业名称、统一社会信用代码等敏感信息直接提交 Git 或日志。
- 训练日志和 rollout 中只保留脱敏后的 sample_id，原始明细放在受控目录。
- 明确 CoT 是真实人工分析、教师模型生成，还是模板拼接；不能把未经验证的推理文本当作事实依据。
- 需要有独立验证集，不能只使用训练 reward 判断模型是否提升。

## 6. CoT 的处理原则

CoT 可以作为训练输入或监督参考，但不能直接把“推理文字看起来合理”当作 reward。

建议将输出拆成两个部分：

1. 结构化最终结论：风险等级、风险分数或是否通过。
2. 可审计依据：引用输入中的字段、计算结果和规则，不要求模型暴露不可验证的内部思维过程。

Reward 优先评价最终结论和依据是否可验证，例如：

- 结论与标签是否一致；
- 风险等级是否满足业务规则；
- 数值计算是否正确；
- 引用的字段是否真实存在于输入；
- 是否出现输入中不存在的事实；
- 输出格式是否符合系统协议。

如果客户明确要求展示 CoT，应先确认合规和业务风险，再决定是否在 rollout 和报告中保存原文。

## 7. Reward 设计建议

金融风控任务不建议一开始使用无法解释的单一语言质量分数。首轮 reward 应尽量由可验证部分组成，并且记录每个子分数。

可以采用如下结构作为讨论起点：

```text
总 reward = 结论正确性 + 数值/规则正确性 + 依据可验证性 + 格式完整性 - 幻觉/越界惩罚
```

具体权重需要由业务目标决定。例如高风险召回比低风险误报更重要时，reward 和最终评测都应体现这一点。

训练前必须记录：

- reward 的理论最小值和最大值；
- 每个子分数的含义和权重；
- 缺失字段如何处理；
- verifier 失败如何处理；
- 无法判断时返回什么分数；
- reward 是否可能超过配置的 `algorithm.max_reward`。

此前数学实验中曾出现“讨论中认为 reward 是 +4/-4，但实际日志表现为 +1/-1”的配置认知差异。NGRPO 的 `max_reward` 必须以实际 reward 函数和运行日志为准。

## 8. RL 是否适合这个金融数据集

在训练前可以做适配性预检查，但不能仅凭“有 30 多维特征和 CoT”判断适合 GRPO 或 NGRPO。

建议先做离线统计：

- 标签分布和高风险样本比例；
- 企业和时间切分是否存在泄漏；
- 每条输入的字段完整率；
- 标签是否稳定、是否存在明显噪声；
- 教师/SFT 模型在验证集上的准确率、召回率和输出格式合格率；
- 同一个 prompt 多次采样时，reward 是否有足够区分度；
- group 中全同 reward、低信息 group 和有效 group 的比例；
- CoT 中引用字段和最终结论的可验证比例。

判断逻辑应是：

- 如果 SFT 模型几乎全部正确，group reward 可能长期全同，RL 学习信号不足。
- 如果 SFT 模型几乎全部错误，group 可能长期全错，RL 也没有足够的正向样本。
- 如果 reward 主要来自不可验证的文本质量，RL 可能优化表达而不是风控判断。
- 如果同一企业或时间窗口发生泄漏，训练提升可能是假象。
- 如果 group 内 reward 有稳定区分，且最终评测可验证，才有必要比较 GRPO 与 NGRPO。

因此，训练前应先完成基座/SFT 模型 rollout 采样和数据画像，再决定训练算法与参数。

## 9. 8 卡资源使用方案

建议先做一次短程链路验证，再进行正式实验：

1. 2 卡或 4 卡：验证数据、reward、prompt、rollout 和日志是否正确。
2. 8 卡：进行正式基线和算法对照，保证同一实验尽量使用相同资源配置。
3. 如果模型较大：根据 HBM、模型并行、FSDP 和 vLLM 的实际占用确定并行方式，不预先承诺某个模型一定能在 8 卡上训练。

正式实验至少保留：

- 一个基座/SFT rollout 基线；
- 一个 GRPO 基线；
- 一个 NGRPO 对照；
- 独立验证集评测；
- 每次实验的 checkpoint、日志、rollout、manifest 和报告材料。

## 10. 建议的开发与实验顺序

### 阶段 A：完成实验元数据和前端配置

- 完成 `run_manifest.json` 生成和读取。
- 前端显示 Reward 定义、范围、CoT、特征维度、镜像、patch、seed、NPU 数量。
- 将“样本不足”和“配置缺失”明确显示为未评估原因。
- 增加 Reward 分布和 Reward 范围图表。

### 阶段 B：建立金融数据预检工具

- 检查字段 schema、缺失值、单位和异常值。
- 检查企业主体和时间切分泄漏。
- 统计标签分布和业务关键指标。
- 检查 CoT、最终答案、参考标签和 verifier 是否可对应。
- 输出数据集画像和训练前风险清单。

### 阶段 C：先做非 RL 基线

- 用基座模型或 SFT 模型生成验证集结果。
- 确认模型能理解 30 多维输入。
- 确认输出协议和 verifier 可用。
- 固定一套独立评测指标作为后续 RL 的比较基线。

### 阶段 D：短程 GRPO 采集验证

- 使用少量 step 验证训练链路。
- 重点检查 group 恢复、reward 范围、CoT/最终答案解析和有效 group 比例。
- 此阶段不作效果结论。

### 阶段 E：正式 GRPO/NGRPO 对照

- 固定模型、数据、prompt、reward、seed、训练预算和资源。
- 先跑 GRPO，再跑 NGRPO。
- 对比训练指标、group 信号和独立验证集效果。
- 只有在证据充分时讨论算法迁移结论。

### 阶段 F：报告和迁移

- 自动生成实验摘要、趋势图、异常样本索引和原始证据路径。
- 将代码、patch、配置模板、数据 schema 和恢复说明同步到 GitHub。
- 模型、镜像和敏感数据使用外部受控制品库，不提交 Git。

## 11. 当前需要讨论并确认的问题

在开始金融风控训练前，建议先和业务、数据和模型人员确认：

1. 风控任务的最终输出到底是分类、排序、分数还是分析报告。
2. 训练标签的来源、时间点和业务含义。
3. 30 多个字段的 schema、单位、缺失值和脱敏方式。
4. CoT 的来源、是否允许保存/展示，以及哪些部分可以自动验证。
5. Reward 的实际范围、子分数和权重。
6. 高风险召回、误报率、准确率和可解释性之间的优先级。
7. 基座模型或 SFT 模型的尺寸、显存占用和 8 卡并行方式。
8. 客户要求的最终评测指标和可接受的模型输出格式。

## 12. 一句话结论

下一步不是直接把金融数据送进 NGRPO，而是先把实验配置、Reward 定义和金融数据画像固定下来，再用基座/SFT 建立可验证基线，之后在相同条件下比较 GRPO 与 NGRPO；这样前端展示的每个结论都能回到原始数据、训练日志和实验配置。
